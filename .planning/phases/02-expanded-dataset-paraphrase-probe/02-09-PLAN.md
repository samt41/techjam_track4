<objective>
Build `arena/datasets/generate.py`: the corpus generator that samples targets, builds the control
arm from the evaluator's own `intent_card`, pins the override turn per pair, drives the authoring
loop through every acceptance gate, and publishes a frozen versioned corpus with its registry entry.

Purpose: this is where D-31, D-36, D-46 and the asymmetric D-35 solvability rule become code. Two
traps live here specifically. First, L-2: D-31's "free verification asset" — a control-arm row and a
bare fallback row producing byte-identical customer behavior — holds for `buying`, `browsing` and
`boundary`, where `behavior_for` returns `{"scenario_type": s}` and never touches the rng, but
CANNOT hold for `intent_override`, where D-36 pins `override["turn"]` from `pair_id` while the
fallback draws `rng.choice([3, 4])` from `f"{sample_id}\0{scenario_type}"`. The unscoped test is
~15% flaky and reads as a corpus bug (D-55). Second, L-3: `.planning/research/ARCHITECTURE.md:258`
explicitly recommends a solvability check, so a diligent implementer will add one to the probe
pipeline — which would delete precisely the sessions carrying the vocabulary gap, report ~0, and
leave every gate green.

Scope note: this plan builds the generator in three right-sized tasks — sampling and assembly,
the gate loop and the solvability asymmetry, then the CLI and publish sequence. The D-31/D-55
fidelity tests and the L-3 solvability-absence AST proof moved to plan **02-14**, which consumes
this module and touches no file this plan writes; folding a 300-line module, a 17-flag CLI and a
four-class test module into one plan put a single task well past the context budget.

Output: `arena/datasets/generate.py` with its CLI, the committed per-pair divergence log, and —
for the probe corpus — the committed target snapshot the catalog-free sweep depends on.
</objective>
