<objective>
Close the two findings that let one agent configuration acquire two identities, and that
let harness output silently replace a record's provenance.

Purpose: MEAS-14's guarantee is that a fingerprinted spec identifies a configuration
reproducibly. It does not hold today. `arena/run_arena.py`'s comment states that an unset
flag is omitted "otherwise one configuration fingerprints two ways", but `--exploration`
defaults to `"disabled"` and `--lexical-mode` to `"auto"`, never `None`, so the filter
never omits them. Verification measured the consequence directly: the default-everything
configuration fingerprints `25e5f553460050d9` through the CLI and `af7bdf3a928ec07f`
programmatically. `adjudicate`'s "a candidate must not share the baseline's fingerprint"
guard can therefore be passed by two specs describing the same configuration. Separately,
`arena/arena.py` splats `**result` LAST over the provenance keys with no collision guard,
while its sibling writer refuses outright on the same hazard.

Why these two together: both are "the record must say what actually ran" defects, both
live on the write path from CLI invocation to published `summary.json`, and their tests
share one file (`tests/test_arena_runner.py` hosts both `SpecFidelityTest` and `CliTest`).
Splitting them would put two plans in contention for the same test module for no benefit.

Output: a CLI whose fingerprint describes the invocation consistently across every entry
path, and a writer that refuses to publish a record that lies about what produced it.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI invocation → fingerprinted identity | The flags an operator types become the hashed `overrides` payload; a fingerprint that describes a configuration other than the one that ran invalidates every comparison built on it |
| harness return value → published provenance | `evaluate()`'s result mapping is splatted over arena-written provenance fields in the record that becomes committed evidence |

Not applicable, with reasons: no network endpoint, no credential or secret, no
authentication or access-control surface, no cryptographic storage claim, no
deserialization of untrusted data on these paths (the CLI's own inputs are validated by
argparse `choices` and by `_existing_file` / `_record_directory`). The operator-supplied
`--output-root` is the one path-shaped input, and it flows through
`resolve_run_directory`'s traversal defence, which plan 01-12 explicitly protects and
this plan does not touch.
