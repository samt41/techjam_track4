    deliberately NOT symmetric in its two arguments: the call site fixes the order

    `paired_bootstrap(baseline, candidate, *, seed, resamples=RESAMPLE_COUNT) -> BootstrapResult` —
    call `_require_paired`, build one `random.Random(seed)` instance, and for each
    replicate draw ONE index vector `[rng.randrange(count) for _ in range(count)]`
    and apply THE SAME vector to both arms, recomputing
    `technical_score(metric_summary(...))` from scratch on each resampled set.
    TechnicalScore is a non-linear function of the sample — Efficiency depends on
    the mean MTTC, not on a mean of per-session efficiencies — so it cannot be
    averaged session-wise (D-17). Comment, at the index-vector line, that drawing
    two independent vectors would silently discard the pairing and inflate the
    standard error roughly sevenfold on this repository's data. Sort the delta
    list; the CI is the percentile pair `deltas[int(0.025 * resamples)]` and
    `deltas[int(0.975 * resamples) - 1]`; `standard_error` is
    `statistics.pstdev(deltas)`; `delta` is the observed difference computed on the
    unresampled arms.

    Use the PERCENTILE interval and record the rejection of BCa in a comment so a
    future reader does not "upgrade" it: BCa needs
    `z0 = NormalDist().inv_cdf(proportion)`, and for two identical candidates that
    proportion is `0.0`, which raises `StatisticsError` — BCa crashes on exactly
    the degenerate fixture D-01 Layer 1 requires. On a near-null pair the delta
    distribution is lattice-valued (26 distinct values in 5,000 replicates, 19.1%
    exact ties), so `z0` swings nineteen-fold on a `<` versus `<=` choice with no
    principled answer.

    `paired_permutation(baseline, candidate, *, seed, resamples=RESAMPLE_COUNT) -> PermutationResult` —
    call `_require_paired`; compute `observed`; for each replicate, iterate the
    pairs and use `rng.getrandbits(1)` to decide, PER SESSION, whether to swap that
    session's two outcomes; recompute the permuted delta from scratch; count when
    `abs(permuted) >= abs(observed) - _TIE_TOLERANCE`. Return
    `p_value = (count + 1) / (resamples + 1)`. Comment the `+1` in both terms: the
    observed assignment is itself a member of the permutation null under
    exchangeability, so a Monte-Carlo permutation p can never honestly be `0.0`,
    only at most `1/(R+1)`. The swap is WITHIN pairs and never across candidates
    (D-18); an independent-sample permutation on the same data would look plausible
    and be wrong.

    `exact_paired_sign_flip_p_value(differences: tuple[float, ...]) -> float` — the
    exact reference: enumerate all `2**n` sign assignments with
    `itertools.product((1, -1), repeat=n)`, compare
    `abs(statistics.fmean(flipped)) >= abs(statistics.fmean(differences)) - _TIE_TOLERANCE`,
    and return `count / 2**n`. Raise `ValueError` when `n` exceeds 20 (the
    enumeration is only tractable there) or when `differences` is empty. Comment
    the deliberate absence of the `+1` here: exhaustive enumeration already contains
    the observed assignment, so adding it again would double-count. This function is
    what pins the two-sided tail convention that `paired_permutation` applies at
    Monte-Carlo scale, against a hand-checkable answer.

    `holm_bonferroni(p_values: tuple[float, ...]) -> tuple[float, ...]` — sort the
    input indices by `(p_values[i], i)` so ties break on the stable input index and
    the result is deterministic. For the rank-`i` (0-based) element of `m`, compute
    `min(1.0, (m - i) * p)`, take a RUNNING MAXIMUM across the sorted sequence, and
    map back to input order. The running maximum is the monotonicity enforcement and
    is the step most commonly omitted; comment it. Without it the adjusted p-values
    can decrease as the raw p-values increase, which is incoherent and can make a
    weaker result look stronger than a stronger one. Raise `ValueError` on an empty
    input or on any p outside `0.0..1.0`.

    The Holm family is the k-1 comparisons of candidates against a common baseline
    in one adjudication event, never candidates crossed with scenarios (D-19). Note
    that in a comment at the function so the caller in plan 01-06 cannot get it
    wrong: folding four scenarios in would inflate the family fourfold, destroy
    power on the one comparison that decides anything, and add power to a Boundary
    bucket of n=10 that can detect nothing regardless.

    `minimum_detectable_difference(standard_error: float) -> float` —
    `MDD_MULTIPLIER * standard_error`, raising
    `ValueError("standard error must be non-negative")` for a negative input.
    Comment why the input is the BOOTSTRAP SE of the delta and not `sd_d / sqrt(n)`:
    TechnicalScore is not a mean of per-session values (D-17), so there is no
    per-session difference whose standard deviation could be taken; the bootstrap SE
    is the SE of the statistic actually being tested, is already computed by
    `paired_bootstrap` at zero extra cost, and inherits the pairing benefit
    automatically. Comment that this value must be reported beside EVERY
    adjudication row including null ones (D-22, MEAS-06) — reporting it is the
    entire mechanism that makes "no significant difference" visibly distinct from
    "we could not have detected one".

    Comment ONE further consequence of the `2.801585218112968` multiplier, because
    plan 01-06 depends on it: since the multiplier bundles the two-sided alpha with
    80% power, `abs(delta) >= MDD` is roughly a 2.8-sigma effect, whose two-sided
    permutation p is around `0.005`. A non-degenerate result that is simultaneously
    at-or-above its MDD and Holm-non-significant is therefore rare by construction —
    it needs a Holm family large enough to inflate `0.005` past `0.05`. That is the
    reason plan 01-06 exposes its verdict decision as an injectable pure helper
    instead of trying to construct such a fixture from session data.

    `expected_max_of_k(k: int, *, panels=_SIMPSON_PANELS, bound=_SIMPSON_BOUND) -> float` —
    the expected maximum of k iid standard normals by composite Simpson integration
    of `x * k * NormalDist().cdf(x) ** (k - 1) * NormalDist().pdf(x)` over
    `[-bound, bound]`. Return `0.0` for `k == 1`; raise `ValueError` for `k < 1` and
    for an odd `panels` (Simpson's rule requires an even panel count). Accumulate
    with `math.fsum` to avoid float drift, then multiply by `width / 3.0`. This
    routine must contain no RNG: the correction has to be byte-reproducible.
    Comment that Blom's approximation `inv_cdf((k - 0.375) / (k + 0.25))` errs by
    2.5e-2 at k=2 against Simpson's 3.8e-15 and is therefore used only as an
    independent cross-check in a test, never as the implementation.

    `winners_curse_correction(standard_error: float, k: int) -> float` —
    `standard_error * expected_max_of_k(k)`. Comment the sigma-hat question
    explicitly, because it decides a Phase 5 go/no-go: the sigma fed here is the
    PAIRED-DIFFERENCE bootstrap SE of the delta (D-21), typically 0.002 to 0.008 on
    this data, and NOT the 0.019 absolute binomial SE of HR@10 quoted in PROJECT.md
    and PITFALLS.md. Those are different quantities and the distinction changes the
    printed number by roughly an order of magnitude, which is why plan 01-07 prints
    sigma-hat, k and `E[max of k]` as separate audited columns.
