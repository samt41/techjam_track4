<objective>
Close the three data-safety findings that can destroy or corrupt a committed baseline
record: `arena/store.py`'s recursive delete on a broad `except OSError`, and
`arena/import_legacy_results.py`'s unguarded, non-atomic, two-file write to an
operator-supplied path.

Purpose: from Phase 1 onward, "a retained historical row" means a committed file rather
than a number in prose (D-04). Every delta in the committed leaderboard is measured
against `experiments/baselines/run-a`, and the whole MEAS-16 anchor lives in
`experiments/baselines/anchor-legacy`. Both are reachable by these two code paths, and
the migration path — the one that by construction writes LOWER-provenance data — is the
one without the guard its sibling already has. The asymmetry is the defect: nothing here
requires new machinery, only that the weaker writer be brought up to the stronger one.

Why these two files together: they are the repository's only two destructive filesystem
paths under `experiments/baselines/`, they share the same failure mode (a committed,
git-tracked record replaced or removed), and they are disjoint from every other file in
this gap-closure round, so this plan runs in wave 1 with no merge surface.

Output: a publish that only deletes what its docstring says it deletes, an import that
refuses rather than clobbers and publishes atomically, and the first test coverage the
legacy importer has ever had.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator-supplied `--output` path → committed record tree | `arena/import_legacy_results.py`'s `--output` is a required, unvalidated `Path` that lands inside `experiments/baselines/`, where every git-tracked baseline record lives |
| filesystem error → destructive recovery | `arena/store.publish` responds to an exception by recursively deleting a directory; the trigger condition decides whether that directory is a crashed corpse or a completed 200-session committed record |
| untrusted JSON file → retained record | The legacy `results.json` is an untracked, provenance-free input that becomes this phase's MEAS-16 validation anchor |

Not applicable, with reasons: no network endpoint and no listening socket; no
credential, token or secret of any kind; no authentication, session or access-control
surface (single local operator, no multi-tenancy); no cryptographic storage claim —
`sha256_file` is documented as an integrity aid and explicitly not an authenticity
control (T-01-09). ASVS L1 categories for those areas have no corresponding component.
