<objective>
Close the auditability warning in `arena/leaderboard.py:155-175` — a record's stored
fingerprint is never compared to the one the reader derives — and record plan 01-10's
Holm-family decision in the payload so it is auditable from the report rather than only
from a source comment.

Purpose: `experiments/RUNS.md:59-64` documents that this exact divergence shipped once
already: a record's stored fingerprint differed from the one the report derived for it,
and because fingerprints seed the bootstrap and permutation streams, the CI, p, MDD and
sigma-hat all silently changed. The remediation was `SPEC_NAME_FIELD` plus a test that
only runs over records that are ALREADY committed. Any new record with a drifted
reconstruction is still reported under a fingerprint that appears nowhere in its own
`summary.json`, and the operator finds out after committing it. The check belongs in the
code path, failing closed, not only in the suite.

Why wave 2 rather than wave 1: this plan writes down the answer plan 01-10 decides — that
a genuinely degenerate arm stays in the Holm family and in `correction_k` — and its
`assumptions` disclosure has to name the field 01-10 adds. It contends with no wave-1
file, so the only reason to sequence it is that dependency.

Scope fence, load-bearing: **this plan must not change a single rendered byte.** Every
edit lands in the JSON payload and in `_spec_from_payload`. `HOW_TO_READ`,
`render_markdown`, `_cell`, `_table` and every table header are owned by plan 01-15,
which regenerates the committed artifacts. Touching a rendered string here would break
`test_the_committed_markdown_matches_the_committed_payload` a wave before anything can
restore it.

Output: a reader that refuses a record it cannot identify, and a payload that states its
own family composition.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| record `summary.json` → reported identity | Every record is reconstructed into a `CandidateSpec` whose derived fingerprint becomes the leaderboard identity, the report's `baseline_fingerprint`, the champion tie-break key, and the RNG seed via `pair_seed` |
| payload `assumptions` → reader's methodology check | The assumptions block is the machine-readable form of the report's methodology claims; a family size a reader cannot see is a claim they must take on trust |

Not applicable, with reasons: no network endpoint, no credential, no authentication or
access-control surface, no cryptographic storage claim, no destructive filesystem action
(this plan writes nothing; `write_leaderboard` is unchanged and out of scope), no
untrusted external input beyond a local `summary.json` that is already parsed with
`json.loads` only and validated by `CandidateSpec.validate()`.
